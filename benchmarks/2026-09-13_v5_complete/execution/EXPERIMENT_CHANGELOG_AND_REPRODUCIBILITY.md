## 2. 数据、复用与评分口径

### 2.1 冻结范围

使用 `benchmark_r1_r5_v5_20260910` 的 `evaluation_labels` 确定评测成员；保留 v3/v4/v5 原件。范围为 6,104 个唯一比较单元、13,000 个选中判断、13,905 个去重模型输入（包括参考端）和每方法 15,616 条原生评分映射。

R1–R5 类别可重叠：R1=2,866、R2=79、R3=733、R4=13、R5=3,600。类别数量不能直接相加作为总样本量。参考题用于原有配对评测，不是训练集或调参验证集。

模型输入仅含题目、原生选项、完整给定证据、输出格式及预算等可见字段。金标、分类理由、目标判断和评分映射不进入生成。M14 恢复原生选项；M17 按独立合格的 VISIT/MANAGE/RESOURCE 子项加载，不把父单元资格自动传给子项。详见[材料化验证](<results_v5_m0_m2_m4_m5/preparation_validation.json>)。

MedRGB 沿用本地六档污染比例 `p_sig=100/80/60/40/20/0`；100 是参考端。各比例独立抽取材料，不能按数组位置假定污染文档与原件一一配对。28 个单元的 77 个上下文包含原有空文档槽位：保留输入，缺失文档不纳入检测评分；纠正文本保留但未进行额外语义判分。

### 2.2 精确复用

比较实际可见输入字段，包括问题、**选项顺序**、固定证据、原生格式和输出预算，并保存来源路径、原 item_id 等溯源信息。不是仅按题号或问题字符串复用。

M3 原 v3 结果共有 4,872 个输入，只有 3,690 个与 v5 精确匹配；其余输入进入 10,215 条续测清单。[复用审计](<results_v5_m3/reuse_audit.json>)验证可见输入、solver/query 模板和方法配置一致。已完成但答案无效或投票平局的旧记录也保留，不挑选性重跑。

最终预测同时包含历史复用和本次生成。因此，完整结果不能描述为“五方法各自从零重跑一次”；单独统计本次推理成本时也不能把复用记录当成本次调用。

### 2.3 评分与失败处理

主表先计算一个比较单元在该类别下的非参考原生任务平均正确性，再对单元等权平均。ALL 在 6,104 个唯一单元上计算，不是 R1–R5 五个百分比的简单平均。另存来源等权均值、全部任务通过率、逐来源/任务、R5 一致性与两端同时正确等指标。

诊断使用已有归一化精确匹配，不添加医学同义词裁判。R4 是 13 个作者预期答案的一致率。原生任务准确率不等同于对每条分类理由做医学语义验证。无效输出、平局和协议失败保留并按原有规则计错，不用金标修复。

M3 新生成结果最终状态：9,926 `complete`、186 `invalid_answer`、88 `vote_tie`、15 `runtime_invalid`。后三类是已产生结果的模型输出结局，不是缺失题目。`runtime_invalid` 包括 query 达到固定输出预算仍没有 `</think>`；不通过不断重试寻找有效答案。传输/执行错误与这些原生输出结局分开处理，技术恢复复用已保存阶段。

## 3. 方法设置：哪些属于实验定义

### 3.1 M0 / M2

保留既有 Llama BF16、提示和解码设置。M2 保留完整 KGCC/KADS、五候选与最终 reranking；固定证据一直可见。每个新输入包含 5 次摘要、1 次探索、5 次候选生成、1 次选择、1 次最终回答，共 13 次生成阶段；7,218 个新输入对应 93,834 次新阶段调用。检索与 reranking 另外审计，不能再次当作 LLM 生成调用相加。

M2 的新增 robustness 最终回答使用既有 JSON 格式和 2,048 token 预算，其余最终回答为 64 token。运行容量采用显存份额 0.75、batch 64；这是本地运行配置，不是新增方法模块。M0/M2 最大上下文设置为 98,304。精确阶段数和 token 统计见[阶段审计](<results_v5_m0_m2_m4_m5/artifact_audit.json>)，复现应读取其原始运行配置而非从本文推断未列出的采样参数。

### 3.2 M4 与 M5 对齐：确实改变过实验配置

用户要求 M4 与 M5 使用相同检索与生成设置、保留不同回答模型。调整发生在此次 M4/M5 正式结果产生之前；变更记录中两者已有预测数均为 0，未把两种 M4 配置的输出混入最终表。

| 设置 | 原 M4 配置 | 本次最终 M4 配置 |
|---|---|---|
| 检索器 | RRF-4 | BM25 + MedCPT 重排 |
| 语料 | TextbooksWikipedia | MedCorp 四语料 |
| 最终检索片段数 | 5 | 8 |
| temperature | 0.2 | 0.7 |
| 追加检索上下文预算 | 128,000 | 30,000 个模型 token |

证据：[完整前后配置](<results_v5_m0_m2_m4_m5/m4_configuration_change.json>)、[M4 配置](<results_v5_m0_m2_m4_m5/configs/m4.json>)、[M5 配置](<results_v5_m0_m2_m4_m5/configs/m5.json>)。配置中保留的 `rrf_k` 字段不能用来证明实际采用了 RRF；实际路径为 BM25+MedCPT。

两者本次均为 question-only 检索的单轮流程、四库每库 BM25 top-32、MedCPT 重排 top-8、temperature=0.7、top_p=1、seed=42、输出最多 2,048 token，保留 CoT/JSON 模板并适配原生任务格式。M5 使用 Qwen3-8B、关闭 thinking；M4 使用 Llama-3.1-8B-Instruct。模型各自的 tokenizer/chat template 不相同。

**论文必须把这项变化写成所采用的基线设置，而不是宣称原 RRF-4 方法仅做了性能优化。** M4/M5 与 M0/M2/M3 的语料、调用次数及预算并非完全一致，不能把所有分数差异仅归因于算法结构。

### 3.3 上下文与推理后端

M4/M5 从安装验证用的 Transformers 路径转为本机 vLLM 0.8.5 批量推理，BF16，启用 prefix caching；复用现有 Transformers 4.51.3 环境。后端或批处理调度变化不保证逐 token 输出一致。

M5 存在超过 32K 的完整原生输入（已记录最长 69,721 token）。运行脚本将 M4/M5 的实际 `max_length` 覆盖为 **131,072**，M5 加入静态 YaRN factor=4、original context=32,768。**M5 JSON 文件仍写着 32,768，不能只复制该 JSON 来声称复现了运行上下文。** 实际依据为[运行脚本](<results_v5_m0_m2_m4_m5/code/run_medrag.py>)。M4 上下文也是 131,072。追加检索片段最多 30,000 个各自模型 token；原题要求的固定证据不裁剪，完整阶段溢出时报错。

## 4. 工程调整与性能证据

### 4.1 M5 / M4：补齐 PubMed 行偏移文件

定位到 PubMed 命中正文读取缺少旁路行偏移文件，导致每条命中可能重新读完整 JSONL 分片。复用已有 `CorpusDocumentResolver` 生成器和 MedRAG 已支持的按偏移读取分支，为全部 1,166 个 PubMed 分片补齐约 182 MiB（191,189,608 字节）偏移文件。

这不是重建语义向量索引，也不是更换检索器。检索策略、正文、文档顺序和采样参数保持。M5 运行中可直接使用，未为此重启；M4 使用相同语料目录与运行代码，随后自动继承。

| 检查 | 实测结果 | 证据 |
|---|---|---|
| 同一组 32 条 PubMed 正文读取 | 4.3263 秒 → 0.001511 秒；正文完全一致 | [读取验证](<results_v5_m0_m2_m4_m5/pubmed_offset_validation.json>) |
| 全部偏移有效性 | 1,166 分片、23,898,701 行，每个字节偏移验证通过 | [全量验证](<results_v5_m0_m2_m4_m5/pubmed_offsets_full_validation.json>) |
| 历史 16 个样本输入等价 | 5 种原生格式，prompt、token IDs、记录 token 数一致，采样设置不变 | [输入等价验证](<results_v5_m0_m2_m4_m5/m5_input_equivalence_validation.json>) |
| 16 题排除检索后的准备时间 | 总计 0.143389 秒 | [准备时间剖析](<results_v5_m0_m2_m4_m5/m5_prompt_preparation_profile.json>) |

最后一项进一步拆成：上下文与消息构造 0.068479 秒、chat template 0.019154 秒、tokenization/长度检查 0.055755 秒。此前对话中的“每题检索约 5.7–6.5 秒、一批准备输入约 90–100 秒”，其“一批准备”口径包含检索循环，不能解释为纯提示拼装需要 90–100 秒。

会话观察到修复后每题检索约 2–3 秒、16 题批准备约 42 秒。这些是共享机器运行观察，不是严格控制的端到端 A/B 实验。32 条读取样本的巨大加速比只适用于该文档读取子步骤，不得写成整个 M5/M4 同倍提速。完整偏移验证证明定位正确，也不等于对所有题目都执行了优化前后生成对照。

适用范围：同样的语料布局与读取路径可用于其他 benchmark，不依赖当前题目内容。M2 已使用较快的 Textbooks/Wikipedia 读取路径；M3 使用另一套内存字典检索服务，不能直接套用这项每题优化。

### 4.2 M2：阶段剖析，未削减完整方法

对三个 batch64 实测：总耗时约 262.52 / 268.65 / 271.39 秒，检索约 62–67 秒、选择约 79 秒、摘要约 38–40 秒、探索约 28 秒、候选生成约 38–39 秒，最终回答约 12–13 秒，reranking 约 1.8–1.9 秒。详见[原始剖析](<results_v5_m0_m2_m4_m5/m2_stage_timing_profile.json>)。

主要成本来自方法内部阶段，未发现可直接照搬 PubMed 缺失偏移的同类大瓶颈。没有为提速删摘要、候选、选择或最终回答。这里记录的是已观察到的瓶颈，而非已完成一个新的 M2 算法优化。

### 4.3 M3：输入准备与一次性检索服务加载

M3 的 `cache=True` 检索服务一次性加载约 57 GiB 的 `id2text.json`，运行观察约 8 分钟启动、展开后约 96 GiB RAM；之后命中文本是字典查找。启动慢与每题提示准备慢是两类成本。没有把正在运行的检索服务替换成偏移读取实现，也未修改其 0.5 秒批处理等待或重排方式。

在新生成阶段写入 `.timing.json`，拆分 preparation、API request、response processing、cache write；检索 JSON 记录其服务往返时间。API request 包括模型生成、传输及客户端处理开销，不是纯 GPU kernel 时间。早期记录的准备步骤约 5–14 ms（tokenizer 首次加载后）、响应处理约 0.33–1.33 秒、缓存写入约 1–48 ms、检索约 2.30–3.97 秒，见[性能调查记录](<results_v5_m3/performance_notes.md>)。

### 4.4 M3：逐 token 熵计算向量化

上游对每个输出 token 单独调用 SciPy entropy；本地改为对 top-logprob 矩阵执行 `entropy(np.exp(top), axis=1)`，对非规则长度输入保留兼容的逐行路径。代码：[response_processing.py](<results_v5_m3/code/response_processing.py>)。

| 测试 | 原实现 | 向量化 | 等价性 |
|---|---:|---:|---|
| 合成 8,192×20 矩阵 | 1.212420 秒 | 0.007853 秒 | 本样本 bit-exact，最大差 0 |
| 8 个非 thinking 候选，共 674 token | 0.110958 秒 | 0.005029 秒 | 全部解析字段完全一致 |
| 1 个 thinking 响应，共 256 token | 0.070735 秒 | 0.002451 秒 | 全部解析字段完全一致 |

证据：[微基准](<results_v5_m3/entropy_microbenchmark.json>)、[真实响应等价验证](<results_v5_m3/response_processing_validation.json>)、[可运行验证脚本](<results_v5_m3/code/check_response_processing.py>)。验证用的附加请求不是正式题目预测。

## 5. 资源调度与不中断范围

### 5.1 机器与并行方式

本次机器有 4 张 NVIDIA H20，编号 **0–3，没有 GPU4**。每卡报告 97,871 MiB 总显存；`nvidia-smi` 的可用量还受驱动保留内存影响。“第 4 张卡”是 GPU3。显存份额、进程实际占用、整卡已用和整卡空闲是不同指标。

M3 的 8 个分片是题目集合，不是模型权重分片：每张卡部署完整 Qwen3-8B，各客户端向一个服务发送自己的题目。输入按初始 prompt token 数、item_id 排序后 `items[shard::8]` 分配，0–6 各 1,277 条，7 为 1,276 条。成员保存在[plan.json](<results_v5_m3/plan.json>)，整个运行没有修改这些原始 ID 集合。

“服务没有停”不等于“所有客户端都没有重启”。调度时仅停止待迁移的客户端，再在新服务上续跑；已有模型服务及未迁移分片继续。已保存结果和中间轮次保留；尚未落盘的在途阶段可能重算。最终零重复证明最终交付 ID 不重复，**不证明中途从未重复执行任何生成请求**。部分控制器的非零退出是这类人工交接产生的，不是模型无效答案或最终缺题。

### 5.2 M4 调度历史

先在 GPU0 受保护借用，保留 6 个正式输入冒烟结果。原批提交到 5,824 条后迁移，合计 5,830 个已完成结果保留，剩余 8,075 条按完整 16 题批切成 4,043 / 4,032，在 GPU0/1 并行。随后两 worker 各提交 1,616 条，合并核对到 9,062 个唯一结果，剩余 4,843 条切为 1,616 / 1,616 / 1,611，在 GPU0/1/2 并行。

### 5.5 监督、其他任务与旧索引

按用户要求约每 5 分钟检查并汇报所有 GPU、累计完成、剩余题数及自上次报告新增题数；检查/汇报本身有耗时，不是严格实时定时器。M3 快照落盘到[supervision.jsonl](<results_v5_m3/supervision.jsonl>)。遇到瞬时 0% 或长题，结合阶段缓存更新时间检查，不仅根据一次 GPU 利用率判断卡死。

会话前段曾使用 Luna max 子代理只读监督；其后按用户指令停止无响应的监督代理，M3 的持续检查由主代理执行。停止监督代理与停止评测进程是不同动作；本文没有完整子代理通信审计，不将代理响应速度作为实验结果。

运行中另一工作区的 iMedRAG 任务多次使用 GPU1/2，显存和计算资源发生变化；未终止这些任务。GPU0、GPU3 原有其他用户任务只在自然退出或满足受保护借用条件后使用。因而整场墙钟耗时混合了资源竞争、启动、分片不均、交接和缓存复用，不适合作为算法之间的公平速度比较。

当前 M4/M5 不依赖先前启动的 Contriever/SPECTER/MedCPT 稠密索引构建。确认依赖关系后停止不需要的 Contriever/SPECTER 构建和启动脚本；MedCPT 自然完成，已有索引文件保留。会话曾记录释放约 15.6 GiB 显存、保留约 271 GiB 索引文件；缺少本文同等完整的清理审计文件，这两个容量仅作历史资源观察，论文无需依赖。

### 10.1 同骨干 M0/M2 对照：不能归因于 Llama 本身

用户进一步指出 M0/M2 同样使用 Llama，却没有 M4 的严重格式问题。核查确认 M4 的模型目录经 `readlink -f` 解析与 M0/M2 均为 `/home/data3/txy/models/LLM-Research-Meta-Llama-3.1-8B-Instruct`。全量评分记录的[同骨干对比](<results_v5_m0_m2_m4_m5/llama_output_comparison.json>)如下，分母仍为 15,616 条映射：

| 方法 | 格式有效率 | 原生有效率 | malformed_json |
|---|---:|---:|---:|
| M0 | 97.43% | 82.17% | 157 |
| M2 | 96.64% | 79.92% | 169 |
| M4 | 61.61% | 46.04% | 3,699 |
| M5 | 93.00% | 75.29% | 27 |

关键差别是最终回答协议。M0/M2 普通任务使用明确的原生格式说明，例如 `The answer must be exactly one option key string, e.g. {"answer":"A"}.`，要求 JSON-only，普通任务最终回答预算 64 tokens、temperature=0。M2 的多阶段推理在最终 reader 之前完成，不能因为它有内部推理就认为其最终 JSON 与 M4 同样复杂。robustness 任务另外允许 errors 数组和 2,048 tokens。

M4 使用 MedRAG 提示词，要求在同一个 JSON 中先写长 `step_by_step_thinking` 再写 `answer_choice`，temperature=0.7、预算 2,048 tokens；普通单选的纯键约束也较弱。长解释字符串内的换行或引号必须转义，否则即使最终答案存在也无法通过严格 JSON 解码。以上是代码中已确认的差异；温度、解释字段、检索上下文各自导致多少差异，尚无受控消融，不能给出独立因果贡献。

具体同题 `s021424`：M0 与 M2 均返回 `{"answer": "A"}`，M4 返回包含长解释的 JSON，答案字段为 `"A. Proceed with liver biopsy"`，M5 返回长解释和纯键 `"A"`。这直接说明同一题上的一部分差异发生在答案表达格式，而不是是否选出 A。本例不代表全量答案语义均正确。

因此更准确的结论是：**当前 M4 的提示词、生成配置与严格评分接口组合存在明显的格式适配问题；不能将其概括为 Llama 不会输出 JSON，也不能将 M4 的低分直接归因于骨干模型较弱。** 这次任务适配与启动检查未充分评估格式失败率，是评测实现上的局限。需要统一输出协议的独立实验才能进一步区分方法能力与接口损失；本次仅诊断并补充记录，没有改写主结果。

按当前证据，本轮还不宜把任何单项修复直接表述为已经确立的新算法贡献。以下是保守定位，不是穷尽相关工作的创新性审查。
