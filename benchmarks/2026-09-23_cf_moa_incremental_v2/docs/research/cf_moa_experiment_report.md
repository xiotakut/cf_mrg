## 1. 计划目标、版本身份与不可变边界

本章历史核心文件是原`cf_moa`[执行计划快照](../../../2026-09-23_cf_moa_process/plan/CF_MED_MoA_Router_Five_Agents_Execution_Plan.md)，SHA-256为`4d27d8ddefd639da24e836f7e95728879c192707986130c4af21a1fa6025b522`。用户先称“cf文件夹”，随后明确更正为`cf_moa`。附件中的历史失败候选并不自动成为采用方法；实际采用入口、配置与原生行为必须回到本地已验证制品核对。

计划研究的是五类操作的互补：A1补全遗漏支持，A2撤销失效支持并重算剩余支持，A3比较固定候选，A4执行给定模型下的干预，A5检查合法无关变化下的稳健性。旧R1实际是分派器，必须先迁出专家位置；旧稳健组件F与新A5始终保留不同身份。Router先按能力和适用范围选择首轮1–2个专家，聚合器依据证据与范围处理提议，最多一次追加检查。不会为“安全”把所有答案强制保持，也不会为“反事实”强制改变答案。

M4/M5在本文中指两套既有骨干及其原生输出配置：M4对应Llama路线，M5对应Qwen路线。它们不只模型名称不同，还可能具有消息构造、模板、结构解码、输出协议、上下文、seed和回退差异；不能把某一套通用默认值覆盖到另一套，也不能将分差全部归于骨干能力。

执行中保留了以下边界：

1. 正式v5、原生评分器、历史基线与已采用单head保持原身份，不用新聚合反写旧结果。
2. 推理只读取当前题合法输入；gold、R标签、分类理由、隐藏配对端及其答案不进入推理。配对关系和correct仅在隔离离线分析中使用。
3. 当前v5范围已经暴露于开发，不称为独立泛化评测。原题与变体仍分别推理；母题/来源家族是统计与切分的重要边界。
4. 原生答案、证据来源、适用范围、修改提议与真实成本分别保存；`unsupported`、不可用、程序错误和错误答案分开记录，失败和未提交样本不从计划分母中删除。
5. 历史响应的请求一致性与输出回放一致性分开验证。真实重采样只确认正式入口、参数、工具与格式，不能要求文本逐字重现，也不能反复抽到旧答案为止。
6. 兼容性修复、方法修订、调参候选和后处理错误分别标注；真实失败不覆盖、不改名。A1-v2明确是新方法版本，不再借用“A1-v1 schema兼容性修复”身份。

用户先要求发现计划或进度冲突即暂停报告，后又授权非重大选择自主推进，并多次限定恢复范围。实际过程因此存在“仅暂停受影响路径”“模型暂停但允许离线准备”“解除A5/F暂停”“保留A5负结果继续旧F”等不同状态。下文按发生时点记录，末尾统一给出当前状态；历史段落中的“尚未开始”不代表该阶段后来仍未执行。

### 2. 统一合同、开发范围与推理/评分隔离

统一层实现 `InputPacket`、`AgentProposal`、来源定位和逐次调用/预算/成本记录。每位专家保留原生提议、适用范围、声明及来源、修改提议、未决项、检查和真实成本；外部知识不能冒充患者事实。引用的原文位置能够被程序核实，但不能因此宣称医学蕴含成立。首次输入结构核查覆盖 13,905 个 v5 输入，确认 `fixed_evidence` 为字符串列表，共 30,065 个字符串元素，没有改写源输入或评分。

开发清单固定为 40 个已暴露家族，每骨干 121 个唯一原生输入、157 条原生评分映射。74 是非 reference 基准评分单元数，不是独立患者数。成员按来源×原生格式×原 R 标签组合分层，每层按固定 SHA 顺序选择家族，并纳入相关原生端点；新模型结果不参与选题。R 标签只用于隔离的离线选择，不进入专家请求。配对账本含 73 对保持、4 对应变，另有 11 条因 reference 或语义资格问题未纳入；不能从 R 类直接要求答案翻转。

推理包只提供白名单原生输入、各骨干自己的完整历史消息与初答、原生输出合同和公开工具/预算。不透明请求句柄不携带来源/R 含义；gold、分类理由、家族、来源 ID 和隐藏配对端保存在隔离评测账本。首次导出误设 M4 评分路径而停止，保留 `development_attempt1_partial/`；纠正真实路径后沿用同一成员，不按分数换题。两骨干共 314 条原生评分映射与历史结果一致，属于离线接口重算，没有新增推理。

运行日志采用 SQLite WAL 和 FULL 同步：提交前保存请求意图，完成后保存原始响应、实际请求与 token 事件；恢复时核对输入、预算、配置和源码指纹，复用同次运行已经落盘的响应。已提交但无响应落盘的情况保留未知用量并阻止自动重抽，不把缺失成本填为 0。后续发现 U+2029 被字符串 splitlines 误切的问题后，明确改为逐物理行读取 JSONL；不能把这项后来的修复写成从未出现读取错误。

### 3. A4：完整采用配置恢复、两层回放及真实请求验收

#### 3.1 公共默认温度覆盖采用版：发现后暂停，按完整配置恢复

### A2：保留完整支持重算，独立检验常数、删除和模型执行解释

**机制控制为何需要。** 复用原 A2 不能只以总分证明“撤销失效支持”有效。需要排除同覆盖常数 None、粗糙删除政策，以及同一事实由模型直接执行的解释。于是锁定原 A2 的 121 输入，其中每骨干九题适用、112 题不适用，复用既有事实与完整支持 trace，预先固定四个 CPU 政策：原完整支持重算、同覆盖常数 None、发现失效路径即删除且不重算其他路径、全部路径重算后只删不新增。两种删除政策仍保留 UNKNOWN 继承与非法初答，不将未提及当否定，也不推断某条路径曾被初答实际采用。

### A3：四个准备缺陷、限定修复与尚未验证的编辑机制

**采用目录头与可选编辑臂必须分开。** 原 A3 是 `legacy_catalog_six_orders_calibrated_majority`，已保存每骨干 121 个提议、八适用/113 不适用；适用范围 M4/M5 正确 3/4 题。编辑臂 `fixed_catalog_bounded_evidence_delta_v1` 默认关闭，仅作为独立反事实实验，不能因为已有目录结果有效就推定编辑流程可运行。

1. editor 的非法 JSON 被捕获后返回 partial 和旧 native 答案，schema/semantic 标志仍为 False，导致 runner 看不到结构失败。

### 13. GPU/CPU衔接：已纠正的流程问题与尚未修复的性能点

多次资源判断没有把旧“四张空闲卡”当持续事实，也没有干预其他健康任务。早期一度误把readout显存比例写为0.95，核完整profile后撤回：两骨干实际为0.85、131072上下文，GPU0当时91687MiB满足约83190MiB初始要求；没有降低配置适配资源。v4固定smoke原GPU3准备后被他人占用，保存未启动manifest，仅换空闲GPU2，参数与固定输入不变。进程锁只能互斥本原型作业，不表示占有共享卡。

用户多次指出空卡与CPU串行延误，记录承认前期重复全范围预检、分层串行审核和任务衔接拖慢GPU；模型本身始终用CUDA/Flash Attention/GPU KV，并非在CPU生成。随后复用未变的全范围请求证据，限定固定请求预检，把记录、控制和终检准备放到模型期间并行。GPU2聚合与GPU0采样，后来GPU0含A1组合与GPU2固定3draw同时计算；空闲GPU3不通过重复有效专家或任意重采来填满。

性能诊断是只读定位，没有热改运行中的源码或宣称完成优化：

- `moa_runner.py:143` 每题调用 `journal.export`，`journal.py:138` 每次解析并重写累计calls与outputs，累积导出工作量呈平方增长。一次观察M4两个导出文件合226572400字节。
- 每draw存在多次prepare/count_tokens路径，原生采样新draw有重复分词；grammar已有按guidance hash缓存，不能写成相同grammar反复编译。EP前102条实际请求分别有102个不同guidance，编译累计292.867秒、均2.871秒、最大10.145秒。

### 8.2 为什么用户观察到GPU空闲，而流程仍耗时

前期CPU工作包括配置核对、schema构建、parser回放、证据定位、统计和日志合并；这些不需要再向GPU发模型请求。真实模型运行并没有改到CPU上。后期两项GPU任务并行：GPU0运行含A1聚合，GPU2运行固定三次采样；GPU1当时有其他健康任务，GPU3没有直接可追加的已准备独立任务。任务结束后的空闲与运行中请求间空档是不同现象。

但实际也存在可避免的调度损失，不能全部用“正在做离线工作”解释。代码显示每题调用`journal.export()`，全量解析和重写累计请求/结果，累计I/O呈平方增长；观察时M4的两个导出文件合226,572,400字节。采样入口还重复计算部分请求token。两个父入口分别绑定单卡、在各自实验内同步执行M4→M5；缺少跨卡统一首错协调，无法在不修改执行器的情况下简单同时开两骨干，否则可能与父进程后续启动冲突。

EP前102条grammar预检实际上对应102个不同guidance，已有按guidance缓存，不能误称相同grammar一直重复编译。记录编译总计292.867秒，平均2.871秒、最大10.145秒。没有测得完整CPU分项墙钟，所以不能把所有GPU停顿都归因于日志或grammar。

已提出的工程改进是增量/后台导出、按完整请求及模型身份缓存token计数、跨卡首错提交协调。**这些改进目前仅完成定位，未实施和验证。** 当时没有热改正在运行且绑定hash的源码，没有为了“用满卡”重生成有效专家或启动暂停臂。另有过多重复检查和启动导入错误造成的延迟，属于执行安排与实现缺陷，应如实承认。性能诊断见[调度记录](cf_moa.md#gpu-cpu-scheduling-diagnosis-20260923)。
